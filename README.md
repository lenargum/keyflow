## Стек

Node 22 + TypeScript + Fastify, PostgreSQL 16 через голый `pg` без ORM,
Vite + React на фронте, Vitest против живой базы.

ORM нет сознательно: оценивают контроль над конкурентностью, а `FOR UPDATE SKIP LOCKED`
в чистом SQL читается сразу и без домыслов.

## Запуск локально

```bash
cp .env.example .env
npm install
npm run db:up
npm run db:reset
```

`db:up` поднимает postgres:16 в docker на порту хоста 5433, `db:reset` накатывает миграции
и сид: 12 товаров, 4 промокода.

Три процесса в отдельных терминалах:

```bash
npm run dev:providers
npm run dev:api
npm run dev:web
```

Заглушки поставщиков на :4001, API с воркером на :3000, витрина на http://127.0.0.1:5173

## Проверка гонок

```bash
npm run test:races
```

Тесты сами поднимают отдельную базу `keyflow_test`, свои экземпляры API и заглушек
поставщиков и гасят их после прогона. Снаружи нужен только `npm run db:up`.
Тот же прогон идёт в CI на каждый push.

| Сценарий | Что проверяется |
|---|---|
| 50 параллельных вебхуков по одному заказу | одна строка в `issuances`, один израсходованный код, `attempts = 1` |
| Повтор вебхука с тем же `event_id` | событие одно, выдача не изменилась побайтово |
| Вебхук раньше заказа | события лежат необработанными, после создания заказа выдача проходит один раз |
| Пустой пул | заказ уходит в `out_of_stock` без падения, после долива ровно один ключ |
| Исчерпаны автоматические попытки | заказ припаркован, ручная выдача из админки даёт один ключ |
| Пять параллельных «выдать повторно» | выдача не изменилась, у поставщика ничего не потрачено |
| Таймаут поставщика | повтор с тем же `request_id` возвращает тот же код, на резервного не уходим |
| Явный `out_of_stock` у A | фолбэк на B, ровно один ключ |
| Двойной клик «Купить» | один заказ: один ответ 201 и один 200 |
| Десять повторов с тем же ключом | один заказ, промокод списан один раз |
| Две покупки без ключа идемпотентности | два независимых заказа, осознанную повторную покупку не ломаем |
| `LIMIT3` под 50 параллельными заказами | ровно 3 применения, остальные 47 получают 409 |
| Сорок предпросмотров скидки | `used_count` не сдвинулся |
| Доступ | `/api/admin/*` и мутирующие QA-ручки отдают 401, вебхук платёжки открыт |

**То же самое кликами.** Страница заказа `/orders/<id>` — QA-панель: оплатить успешно или
неуспешно, повторить последний вебхук, 50 вебхуков разом, выдать повторно, ползунки долей
ошибок и зависаний у поставщиков, опустошение и долив пула. Рядом живой лог вебхуков.

Админка `/admin` — список «оплачен, но код не выдан», безопасная повторная выдача, расход
промокодов, сценарий «вебхук раньше заказа» и сброс демо-состояния. Мутирующие ручки
закрыты токеном `ADMIN_TOKEN`: он передан отдельно вместе со ссылкой и вводится один раз
на странице админки.

## Как обеспечена однократная выдача

Никаких «прочитал — проверил — записал»: каждый переход состояния это один атомарный
SQL-стейтмент, и каждая гарантия продублирована констрейнтом, чтобы баг в коде упирался
в отказ базы, а не в задвоенный ключ.

- `issuances.order_id UNIQUE` — заказ физически не может получить две выдачи
- `payment_events.event_id PRIMARY KEY` плюс `INSERT ... ON CONFLICT DO NOTHING` — повтор вебхука отсекает база
- захват заказа воркером — `UPDATE ... FOR UPDATE SKIP LOCKED` с переходом в `delivering` в том же стейтменте
- `orders.idempotency_key UNIQUE` — двойной клик по «Купить» это такая же гонка, как повтор вебхука, и закрыта она так же: клиент шлёт заголовок `Idempotency-Key`
- `promocodes` — `UPDATE ... WHERE used_count < max_uses` одним стейтментом, сверху страхует `CHECK (used_count <= max_uses)`

**Ловушка таймаута.** `request_id = req_<order_id>` детерминирован от заказа, а не от номера
попытки, поэтому поставщик обязан вернуть по нему тот же код. После таймаута мы
переспрашиваем того же поставщика, а на резервного уходим только на явный `out_of_stock`:
таймаут значит «возможно, уже выдал», и фолбэк на B стоил бы двух потраченных кодов.

**Границы транзакций.** Три места, где два запроса подряд оставляли окно для потери:

- захват события оплаты и его применение к заказу: падение между ними пометило бы событие
  обработанным, оставив заказ неоплаченным навсегда, и повтор вебхука не спас бы —
  тот же `event_id` отсекается первичным ключом
- запись выдачи и перевод заказа в `delivered`: падение между ними оставило бы код
  записанным, а заказ навсегда в `delivering`
- списание промокода и вставка заказа: иначе упавшая вставка сжигала бы использование

Все три сведены в одну транзакцию.

**Вебхук отвечает `200 OK` до похода к поставщику.** Иначе зависший поставщик роняет ответ,
платёжка ретраит по контракту at-least-once, и мы сами себе устраиваем шторм вебхуков.

## Промокоды

`POST /api/orders` принимает `{sku, promo_code?}` и только это. Цену клиент не присылает:
базовая сумма берётся из `products`, скидка считается на сервере, итог не уходит ниже нуля.

Использование резервируется при создании заказа, а не при оплате, и при неуспешной оплате
не возвращается. Критерий требует «применён не более N раз» — резерв на входе выполняет это
строго, без окна на возврат, в котором лимит обходится.

### Как покупатель видит скидку, если считать её на клиенте нельзя

Требование «данным от клиента не доверять» запрещает считать деньги на клиенте, но не
запрещает серверу рассказать, что получится. `POST /api/promocodes/preview` отдаёт готовые
суммы, клиент их только рисует: карточка выводит `total` и `base` как есть и ничего
не перемножает.

- **Предпросмотр ничего не мутирует.** Тест шлёт сорок запросов и проверяет, что `used_count` не сдвинулся.
- **Предпросмотр и списание считают одной функцией.** Показанное не может разойтись со списанным.
- **Предпросмотр не обязательство.** Лимит может исчерпать кто-то другой, поэтому заказ всё равно списывает использование атомарно и вправе ответить 409.
- **Остаток применений наружу не отдаём.** Ручка публичная: по убыли счётчика можно было бы считать чужие заказы. Остаток видит оператор в админке.

## Вёрстка витрины

Свёрстан верх витрины по макету: шапка, баннер-карусель, ряд иконок сервисов, блок
пополнения Steam, ряд карточек товара, раскрытое меню каталога. Отзывы, футер, остальные
ряды карточек, мобильная и тёмная версии исключены заданием.

Дизайн-токенов в макете нет, поэтому цвета и тени сняты посекционно и собраны
в `web/tailwind.config.js`. Иконки выгружены из макета в `web/public/figma/`.

Пять обязательных точек интерактива: карусель с автопрокруткой, стрелками и бесшовной
закольцовкой; меню каталога с закрытием по клику вне и по Escape; переключатель валют,
подхватываемый в сумме и в кнопке оплаты; ховер иконок сервисов; ховер карточек.

Карточки наполняются реальным каталогом из БД: «Купить» на любой из двенадцати создаёт
настоящий заказ. Табы фильтруют по типу товара.

## Деплой и CI/CD

Пуш в `main` → типы трёх пакетов → сборка фронта → тесты гонок против настоящего
Postgres → деплой. Деплой идёт только после зелёных тестов.

Ключ деплоя прописан на сервере с forced command: шелла он не даёт и умеет запустить
только скрипт деплоя. Работает под непривилегированным пользователем, `sudo` разрешён
ровно на рестарт двух сервисов. Секреты сгенерированы на сервере и в репозиторий
не попадают. Фронт и API отдаются с одного origin, поэтому CORS не нужен вовсе.

**На сервере Postgres поставлен нативно, без Docker.** Машина общая с другими сервисами,
а Docker переписывает правила фаервола — на общем сервере это лишний риск ради удобства,
которое здесь не нужно. Локально `docker compose` используется как обычно.

## Что осознанно не делали

Redis и очереди — поллер живёт в том же процессе. Пользовательскую авторизацию — только
статический токен для админки, задание её снимает. DI-контейнеры, репозитории,
гексагональную архитектуру. Экспоненциальный бэкофф — фиксированные интервалы. Метрики
и трейсинг — `console.log` с `order_id`. Проверку подписи вебхука — задание её снимает.

**Сверку `amount` из вебхука с суммой заказа** — тоже сознательно. Задание говорит «только
реакция на статус», а главное: правильная реакция на расхождение это не отказ в выдаче
(деньги уже пришли), а выдача с пометкой на ручной разбор. Это отдельный workflow,
которого задание не просит.
