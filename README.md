# Keyflow — магазин цифровых товаров

Тестовое задание: однократная выдача ключей под гонками и восстановление после сбоев.

Проектное решение целиком описано в
[docs/superpowers/specs/2026-08-31-keyflow-architecture.md](docs/superpowers/specs/2026-08-31-keyflow-architecture.md).

## Стек

Node 22 + TypeScript + Fastify, PostgreSQL 16 через голый `pg` без ORM,
Vite + React на фронте, Vitest против живой базы.

ORM нет сознательно: оценивают контроль над конкурентностью, а `FOR UPDATE SKIP LOCKED`
в чистом SQL читается сразу и без домыслов.

## Запуск локально

```bash
cp .env.example .env
npm install
npm run db:up        # postgres:16 в docker, порт хоста 5433
npm run db:reset     # миграции + сид: 12 товаров, 4 промокода
```

Три процесса в отдельных терминалах:

```bash
npm run dev:providers   # заглушки поставщиков A и B, :4001
npm run dev:api         # API + воркер, :3000
npm run dev:web         # витрина, :5173 (проксирует /api на :3000)
```

Витрина — http://127.0.0.1:5173

## Проверка гонок

```bash
npm run test:races
```

Тесты сами поднимают отдельную базу `keyflow_test`, свои экземпляры API (:3100)
и заглушек поставщиков (:4101), гасят их после прогона. Ничего запускать заранее не нужно,
кроме `npm run db:up`.

Что проверяется:

| Сценарий | Проверка |
|---|---|
| 50 параллельных вебхуков по одному заказу | ровно одна строка в `issuances`, ровно один код израсходован, `attempts = 1` |
| Повтор вебхука с тем же `event_id` | событие одно, выдача не изменилась побайтово, у поставщика ничего не потрачено |
| Вебхук раньше заказа | события лежат необработанными, после создания заказа выдача проходит один раз |
| Пустой пул | заказ уходит в `out_of_stock` без падения, после долива ровно один ключ |
| Таймаут поставщика | повтор с тем же `request_id` возвращает тот же код, на резервного не уходим |
| Явный `out_of_stock` у A | фолбэк на B, ровно один ключ |
| Исчерпаны автоматические попытки | заказ парковался, ручная выдача из админки дала ровно один ключ |
| Пять параллельных «выдать повторно» по доставленному заказу | выдача не изменилась, у поставщика ничего не потрачено |
| Доступ | `/api/admin/*` и мутирующие QA-ручки отдают 401 без токена, вебхук платёжки открыт |
| `LIMIT3` под 50 параллельными заказами | ровно 3 применения, остальные 47 получают 409 `promo_limit_reached` |
| Расчёт скидки | процент и фиксированная сумма считаются на сервере, цена от клиента игнорируется, сумма не уходит в минус |
| Неизвестный промокод | 409, заказ не создаётся |

То же самое кликами.

**Страница заказа** `/orders/<id>` — QA-панель: оплатить успешно/неуспешно, повторить
последний вебхук, 50 вебхуков разом, выдать повторно, ползунки долей ошибок и зависаний
у обоих поставщиков, кнопки опустошения и долива пула. Рядом — живой лог вебхуков
с отметками получения и применения.

**Админка** `/admin` — список «оплачен, но код не выдан» с кнопкой безопасной повторной
выдачи, состояние пулов поставщиков, сценарий «вебхук раньше заказа» и полный сброс
демо-состояния. Дизайна нет намеренно: задание требует рабочего вида.

Токен вводится в поле `ADMIN_TOKEN` на странице админки и хранится в localStorage.
Локально подставляется `dev-admin-token` из `.env.example`.

## Вёрстка витрины

Свёрстан верх витрины по нодам макета `FvqZhoweBeePOboFRZiOJ7`: шапка (`1:598`),
баннер-карусель (`1:641`), ряд иконок сервисов и блок пополнения Steam (`1:494`),
ряд карточек товара (`1:145`), раскрытое меню каталога (`1:1193`). Отзывы, футер,
второй и третий ряды карточек, мобильная и тёмная версии исключены заданием.

Дизайн-токенов в макете нет — `get_variable_defs` отдаёт только две тени. Цвета,
отступы и тени сняты посекционно через `get_design_context` и собраны в
`web/tailwind.config.js`. Иконки и картинки выгружены из макета в `web/public/figma/`
(PNG сжаты до 144px: 2.5 МБ → 196 КБ).

Пять обязательных точек интерактива:

| № | Точка | Что делает |
|---|---|---|
| 1 | Баннер-карусель | автопереключение раз в 5 секунд, стрелки с закольцовкой, шесть кликабельных точек-индикаторов |
| 2 | Кнопка «Каталог» | открывает меню, закрывается повторным кликом, кликом вне и по Escape |
| 3 | Переключатель валют | `$ / ₸ / ₽` меняют активное состояние и подпись кнопки оплаты, пересчёта нет — задание его не требует |
| 4 | Иконки сервисов | плавный подъём с усилением тени и лёгким зумом иконки |
| 5 | Карточки товара | подъём и усиление тени при наведении |

Карточки наполняются реальным каталогом из БД, а не статикой: «Купить» на любой
из двенадцати создаёт настоящий заказ. Изображение у карточек одно на всех — то же,
что в макете; в каталоге из приложения к заданию реальных картинок нет.

## Промокоды

`POST /api/orders` принимает `{sku, promo_code?}` — и только это. Цену клиент не присылает:
базовая сумма берётся из `products`, скидка считается на сервере (`percent` — процент с
округлением вниз, `amount` — фиксированные рубли), итог не может уйти ниже нуля.

Списание использования и создание заказа идут в одной транзакции: если вставка заказа
упадёт, использование промокода откатится вместе с ней.

Использование резервируется при создании заказа, а не при оплате — возврата при неуспешной
оплате нет. Это осознанный выбор: критерий приёмки требует «применён не более N раз»,
и резерв на входе выполняет его строго, без окна на возврат, в котором лимит можно обойти.

## Как обеспечена однократная выдача

Каждый переход состояния — один атомарный SQL-стейтмент, никакого
«прочитал — проверил — записал». Каждая гарантия продублирована констрейнтом,
чтобы баг в коде упирался в отказ базы, а не в задвоенный ключ:

- `issuances.order_id UNIQUE` — заказ физически не может получить две выдачи
- `payment_events.event_id PRIMARY KEY` + `INSERT ... ON CONFLICT DO NOTHING` — повтор вебхука отсекает база
- захват заказа воркером — `UPDATE ... FOR UPDATE SKIP LOCKED` с переходом в `delivering` в том же стейтменте
- `request_id = req_<order_id>` детерминирован: сколько бы раз ни ретраили, поставщик обязан вернуть тот же код
- ручная повторная выдача не выдаёт код сама, а возвращает заказ в очередь — тот же `request_id` плюс UNIQUE не дают задвоиться
- лимит промокода держит `UPDATE ... WHERE used_count < max_uses` одним стейтментом, сверху страхует `CHECK (used_count <= max_uses)`
- после таймаута переспрашиваем того же поставщика, на резервного уходим только на явный `out_of_stock` — таймаут значит «возможно, уже выдал»

Вебхук отвечает `200 OK` до всякого похода к поставщику. Иначе зависший поставщик
роняет ответ, платёжка ретраит по контракту at-least-once, и мы сами себе устраиваем
шторм параллельных вебхуков.
